<Visibility for="agents">
**Quando ler esta página:** quando for montar ou sincronizar o diretório da agência: a estrutura `clientes/<organização>/<cliente>/{operacao, comercial}`, o que vai em cada arquivo, como manter as pastas iguais às organizações do painel e como usar o Git.
</Visibility>

A agência trabalha com o assistente num diretório só. As pastas espelham a
Zatten: cada **organização** do painel é uma pasta, e cada cliente fica dentro da
organização em que o projeto dele está. Dentro do cliente, a **operação** (o que o
assistente configurou) e o **comercial** (a venda e o relacionamento) ficam
separados. Na primeira vez, o [setup](/trabalhar-com-ia/setup) monta tudo.

## A estrutura

```text
minha-agencia/
  AGENTS.md            regras fixas, lidas pelo Codex, Cursor e outros
  CLAUDE.md            aponta para o AGENTS.md (o Claude Code lê este)
  AGENCIA.md           quem é a agência; lido em toda sessão
  .gitignore           .env fora do versionamento
  clientes/
    Implantação/                 o nome da organização no painel
      clinica-sorriso/
        CLIENTE.md               quem é, project_id, estágio, site, regras
        operacao/
          MEMORIA.md             ## Vigente e ## Histórico
          snapshots/             AAAA-MM-DD_HHMM_<assunto>.json
          .env                   chaves do cliente (nunca versionado)
        comercial/
          diagnostico.md         o diagnóstico da venda
          proposta-AAAA-MM-DD.html
          viabilidade-AAAA-MM-DD.md   interna: custo, preço e margem
          historico.md           conversas, follow-ups, contrato
    Produção/
      imobiliaria-norte/
        ...
```

**Todo mundo é cliente.** Não existe pasta separada de prospect: o estágio do
cliente (prospect, em implantação, em produção…) é a **organização** do projeto, e
fica anotado no `CLIENTE.md`. Um cliente que ainda não tem projeto na Zatten (só a
conversa e a proposta) fica na organização de estágio inicial que a agência usa;
o `project_id` entra no `CLIENTE.md` quando a demo nasce.

## As pastas seguem o painel

A Zatten manda. Sempre que um `list_projects` mostrar diferença em relação às
pastas, o assistente lista o que mudou e, com um "sim", sincroniza:

| Mudou no painel | No computador |
|---|---|
| Projeto mudou de organização | `git mv` da pasta do cliente para a organização nova |
| Projeto novo | Pasta nova, com o `CLIENTE.md` preenchido pelo `get_template` |
| Organização renomeada | A pasta da organização é renomeada |
| Projeto apagado no painel | A pasta fica; o `CLIENTE.md` ganha a nota "projeto apagado em …" |

Cada sincronização entra no Histórico do cliente e vira um commit. Mudar o
cliente de estágio pelo assistente é o caminho inverso: `move_project` na Zatten,
e a pasta vai junto.

## O que vai em cada arquivo

### AGENTS.md e CLAUDE.md

As regras fixas da skill, para valerem mesmo quando a skill não for carregada. O
Claude Code lê `CLAUDE.md`; o Codex e o Cursor leem `AGENTS.md`. Por isso o
`CLAUDE.md` só aponta para o `AGENTS.md`, e as regras ficam num lugar.

### AGENCIA.md

O documento da agência, compartilhado por todos os clientes. Sai do diagnóstico
da agência, no [setup](/trabalhar-com-ia/setup):

- site da agência (o assistente lê o site para completar o resto);
- o que vende hoje, para quais nichos e o ticket médio;
- quantos clientes ativos;
- como vende: canal, processo comercial, quem vende;
- quanto cobra pela solução de IA (setup e mensalidade) e quantos clientes quer
  colocar nela;
- como trata os clientes (tom, prazos, o que entrega todo mês);
- o **progresso do setup**, para retomar;
- as **dicas já dadas** e as **chamadas comerciais recusadas** (com a data), para
  o assistente não repetir.

### CLIENTE.md

O contexto de um cliente final, na raiz da pasta dele:

- `project_id` e o **nome exato** do projeto, como vêm de `list_projects`;
- o estágio (a organização) e o site;
- nicho e o que o cliente vende;
- objetivos (por exemplo, "agendar avaliação", "qualificar antes de passar ao
  corretor");
- regras do cliente ("nunca falar preço pelo WhatsApp").

É preenchido no [diagnóstico](/trabalhar-com-ia/diagnostico), na primeira vez que
o assistente abre o cliente. O que não dá para inferir do projeto, ele pergunta.

### operacao/MEMORIA.md

Duas seções, com papéis diferentes:

- **Vigente:** o que vale hoje. Reescrita quando muda. Inclui a última `revision`
  conhecida do projeto.
- **Histórico:** só acrescenta, nunca reescreve. Uma entrada datada por evento.

Cada entrada do Histórico traz:

- data;
- o pedido;
- o que mudou;
- o que não foi feito e por quê;
- o que ficou para fazer no painel;
- o nome do snapshot.

Mudanças feitas por outra pessoa no painel também entram, como "mudança externa".
Veja [Mudanças feitas pelo painel](/trabalhar-com-ia/mudancas-pelo-painel).

### operacao/snapshots/

O template do projeto lido **depois** de cada escrita, com nome
`AAAA-MM-DD_HHMM_<assunto>.json`. Serve para dois fins:

- **perceber mudança externa:** se a revision do projeto mudou, o assistente
  compara o estado atual com o último snapshot e diz o que mudou;
- **desfazer à mão:** a Zatten guarda versões só do agente. Colunas, tags e
  automações não têm histórico, e o snapshot é o único registro do estado
  anterior.

**O snapshot nunca leva chave.** O `get_template` devolve credenciais preenchidas;
antes de gravar, o assistente troca por `"<removido>"`:

- todo campo `api_key` (do modelo, dos modelos de reserva, da transcrição, do
  LangSmith, do motor antigo e `eleven_labs_api_key`);
- os valores de todos os `headers` (de tools HTTP, servidores MCP e ações
  personalizadas);
- os valores de `query_params` e `body_params` das ações personalizadas.

Endereços (`url`, `webhook_url`) ficam, porque o diff precisa deles. Ao usar um
snapshot para desfazer, nunca devolva um campo com `"<removido>"`: omita-o, e a
Zatten mantém o valor atual.

Um snapshot por escrita basta: o "antes" de uma escrita é o "depois" da anterior.

### operacao/.env

As chaves do cliente, uma por linha:

```bash
ZATTEN_API_KEY=...      # a chave de API do projeto, para a API do dia a dia
LANGSMITH_API_KEY=...   # se o LangSmith estiver ligado, para ler os traces
```

O `.env` precisa estar no `.gitignore` **antes** da primeira chave. A pessoa cola
as chaves direto no arquivo, ou o assistente copia a do LangSmith que veio no
`get_template` — e só para cá, sem mostrar na conversa
([regra 11](/trabalhar-com-ia/regras)).

- [API do dia a dia](/trabalhar-com-ia/api-do-dia-a-dia)
- [Extrair dados do LangSmith pela API](/engenharia-de-ia/langsmith)

### comercial/

Tudo da venda e do relacionamento com aquele cliente: o diagnóstico, as propostas
(HTML pronto para imprimir em PDF), a viabilidade interna e um `historico.md` com
reuniões, follow-ups e o contrato. Veja [Vender com o Zatten-OS](/vender/visao-geral).

## Um cliente ativo por vez

No início da sessão, o assistente declara com qual cliente vai trabalhar e usa o
`project_id` do `CLIENTE.md`. Ele não adivinha o projeto pelo nome.

Outro cliente só entra como leitura e citado em voz alta: "usando o follow-up da
Clínica Sorriso como referência para a Imobiliária Norte". Escrever em dois
clientes na mesma tarefa exige dois planos e dois "sim".

## Git

O setup inicia o Git no diretório: `git init`, o `.gitignore` com `.env` **antes**
da primeira chave, e o primeiro commit. Depois, o assistente faz um commit por
mudança aplicada (o snapshot e a memória juntos) e um por sincronização de pastas.

Para quem nunca usou: o Git guarda cada versão dos arquivos. Com ele, dá para ver
o que mudou num cliente em qualquer dia e voltar um arquivo ao que era. A Zatten
guarda versões só do agente; colunas, tags e automações não têm histórico, e o Git
com os snapshots é esse histórico. O assistente cuida dos commits; a pessoa não
precisa digitar nada.

## Armadilhas

- **Snapshot gravado com chave.** Se um snapshot antigo foi salvo antes desta
  regra, ele tem chaves dentro: apague-o ou troque os valores por `"<removido>"`,
  e confira que ele nunca foi para um commit.
- **`.env` fora do `.gitignore`** vaza a chave do projeto no primeiro commit. A
  skill confere isso, mas confira também.
- **Nome do projeto mudou no painel.** O MCP exige o nome exato. Se a escrita for
  recusada por nome, atualize o `CLIENTE.md` com o nome que veio de
  `list_projects`.
- **O Vigente não substitui o snapshot.** O Vigente é texto escrito pelo
  assistente; só o snapshot dá para comparar com o projeto.
